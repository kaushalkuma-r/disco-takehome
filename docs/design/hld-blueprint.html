01 · Product & requirements

One sentence: an advertiser describes their business; Campaign Studio returns where to run (ranked publishers with reasons and exclusions), who to speak to (persona-tuned creative), and how to run it (a structured, editable config) — with the reasoning visible at every step.

Baseline (from the brief)

ReqRequirementAcceptance
R1Ranked publishers with reasoning≥3 recommended with a per-publisher reason and score breakdown; ≥3 exclusions with reasons
R23–5 creative variants, one per personaHeadline ≤80 chars, body ≤240 chars, CTA; persona fit score + "why this persona" shown
R3Structured campaign configObjective, KPI, bid strategy + ranges, budget (daily/total/flight), targeting, per-publisher allocation summing to 100, creatives linked to placements
R4Handle messy inputVague input never yields a confident plan: clarity score <60 triggers questions; off-topic (B2B SaaS) yields an honest "weak fit" plan
R5Show your workEvery number on screen has a rationale one click away
R6Prompts in prompts/, one-page README, runnable with one command—

Product features (our additions)

Non-negotiable

Login & workspaces

Supabase Auth (email + Google). Every campaign belongs to a user. Reviewers sign up in 10 seconds.

Impact

Input clarity gate

LLM scores clarity 0–100 and extracts signals. Below 60 it asks up to 3 multiple-choice questions before generating. Directly attacks the "messy input" hard part.

Impact

Explainable scoring

Deterministic pre-score (category 35 · persona 30 · AOV 15 · audience 20) + bounded LLM adjustment with written reason. Breakdown bars per publisher.

Impact

History & compare

Every run is versioned. Pick two runs, see publisher score deltas and headline decisions side-by-side.

Impact

Editable config + export

Inline edits, budget sliders that must sum to 100, single-creative regenerate. Export PDF brief and config JSON.

Impact

Chat workflow

The same pipeline driven conversationally: brief → clarifying questions → campaign card → "drop Swiftcart", "make B punchier", "export as PDF". Tool-calling over the same service layer.

Non-goals

  • Real auction / pacing simulation, image creative, multi-tenant orgs and roles, billing.
  • Fine-tuned models — prompt engineering plus deterministic scoring is the honest scope for 6–8 hours.

Deterministic pre-score (the part we can unit-test)

score = 0.35·category + 0.30·persona + 0.15·aov + 0.20·audience      # each 0–100

category : Jaccard-style overlap between brief.categories and publisher.category ∪ subcategories,
           with a curated adjacency table (pet_food ~ pet_supplies = 0.8, groceries ~ pet_food = 0.3)
persona  : mean fit of the top-3 personas that are plausible for the publisher's audience
aov      : 100 − clamp(|log(brief.price_point / publisher.aov)| · 60)   # order-of-magnitude distance
audience : age-band overlap · gender-skew compatibility · income-tier distance

LLM adjustment is bounded to ±15 and must cite a publisher note. Anything < 40 after adjustment is "excluded".
Why hybrid, not pure LLM: the LLM alone will happily rank Velvetline for dog food if the prompt is slightly off, and it can't explain a number it invented. A deterministic backbone makes rankings reproducible, testable, and cheap; the LLM adds judgment (a note like "skeptical of unsubstantiated health claims" should hurt a supplement brand) and writes the reason. That boundary is also the most interesting engineering in the problem.

  S->>LLM: personas.md → 3–5 personas, fit, why

  }
  campaigns {
    uuid id PK
    uuid user_id FK
    text name
    text brief
    jsonb clarity
    jsonb parsed_brief
    jsonb publishers
    jsonb excluded
    jsonb personas
    jsonb creatives
    jsonb config
    text status
    int version
    timestamptz created_at
    timestamptz updated_at
  }
  campaign_versions {
    uuid id PK
    uuid campaign_id FK
    int version
    jsonb snapshot
    text change_note
    timestamptz created_at
  }
  chat_messages {
    uuid id PK
    uuid user_id FK
    uuid campaign_id FK
    text role
    jsonb content
    timestamptz created_at
  }
  • JSONB for generated artifacts. Rankings, creatives and config are documents that change shape as prompts evolve; normalising them buys nothing at this scale. Each is validated by a Pydantic schema on write.
  • Versions as snapshots. Every edit copies the full campaign into campaign_versions; compare works on any two versions or campaigns.
  • RLS on every table (user_id = auth.uid()) even though FastAPI is the only client — defense in depth, and it lets the frontend read directly later if we want.
  • Publishers and personas stay in the repo's JSON for the prototype; the schema reserves publishers/personas tables for scale.

State & data flow

  • Supabase session in memory + localStorage (their SDK). api.ts attaches Authorization: Bearer.
  • Server state with TanStack Query (campaign list, campaign by id) — mutations update the cache optimistically (drop publisher, edit creative) and roll back on error.
  • Generation uses SSE: the wizard's progress list is driven by real stage events, not a timer.
  • Auth guard is a client component: unauthenticated → /login. Static export means no middleware; acceptable because the API is the real guard.

10 · Build plan & intentional cuts

Order of work (fits 6–8 h with AI tooling)

  1. Backend skeleton — FastAPI, settings, auth dependency, catalog loader, schemas, /healthz. Deterministic scoring.py with tests. 1.5 h
  2. Pipeline — clarity, rank, personas, creative, config; prompts in prompts/; recorded-fixture tests. 2 h
  3. Frontend — shadcn scaffold, login, wizard, campaign tabs, history. 2.5 h
  4. Chat + export — tool-calling endpoint, PDF template. 1 h
  5. Deploy — Dockerfile (Shape A) on Railway; Vercel project for Shape B; README. 1 h

Cut on purpose

  • Image creative, A/B test simulation, real CPM data — the brief says text and "sensible" numbers.
  • Org/team roles — a single-user workspace proves login and persistence.
  • Vector search — 20 publishers fit in one prompt; the scale section shows where it goes.
  • PPTX export — one export format done well beats two done adequately.

Hard vs easy

Genuinely hard

Scoring that is both explainable and right at the margins (Pantrygood for dog food?). Copy that reads persona-specific without parroting the persona's keywords. Deciding when input is "vague enough" to interrupt the user. Keeping LLM JSON stable under prompt changes.

Easy

CRUD, auth wiring, the config shape, PDF, the chat loop once the services exist. The frontend is work, but not risk.

Where the interesting engineering lives: the boundary between deterministic scoring and LLM judgment, and the eval harness that tells you whether a prompt change made rankings better or just different.
