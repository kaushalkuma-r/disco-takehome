01 · System overview

Every user action that touches the model is an interaction inside a thread (one thread per campaign). The wizard, the chat, and the feedback buttons are three front doors into one orchestrator, which only ever calls typed tools, then runs validators, then charges credits from real token usage, then persists a version.

02 · Agent core internals

2.1 Orchestrator state machine

stateDiagram-v2
  [*] --> Authorize
  Authorize --> Estimate: user ok
  Estimate --> Rejected: balance < base cost
  Estimate --> Plan: reserve(base)
  Plan --> CallTool: next tool from plan (guided) or LLM tool-choice (free)
  CallTool --> Validate: tool returns
  CallTool --> Failed: tool error after retry
  Validate --> Repair: failures && repairs < 2
  Repair --> CallTool: re-call the tool named by the failing check, with error attached
  Validate --> Persist: ok or repairs exhausted (warnings kept)
  Plan --> Persist: plan complete
  Persist --> Settle: write version + validation_results
  Settle --> Done: charge actual usage
  Failed --> Release: refund reservation
  Rejected --> [*]
  Release --> [*]
  Done --> [*]

03 · Tool registry

A tool is a class with typed Input/Output Pydantic models, a cost descriptor and an async run(ctx, input). The registry exports OpenAI function schemas from the same models, so chat and code paths can't drift.

class Tool(Generic[I, O]):
    name: str; description: str
    Input: type[I]; Output: type[O]
    cost: Cost              # Cost(base=10, usage=True) | Cost.free()
    mutates: bool           # True → bumps campaign version + runs validators
    async def run(self, ctx: AgentCtx, inp: I) -> O: ...

@register
class RankPublishers(Tool[RankIn, RankOut]):
    cost = Cost(base=0, usage=True); mutates = True
    async def run(self, ctx, inp):
        pre = scoring.prescore(ctx.campaign.parsed_brief, ctx.catalog)        # deterministic
        top = pre[:10]
        out, usage = await llm.call("rank", RankOut, {"brief": ..., "candidates": top, "memory": ctx.memory})
        ctx.usage.add("rank", usage)
        return merge_bounded(pre, out, max_delta=15, exclude_below=40)

04 · Validators & repair

Validators are pure functions (Campaign, Catalog) → ValidationResult. They run after every mutating tool and are stored per interaction; the campaign page shows them as a Checks panel. A failing check names the tool that can fix it; the orchestrator re-calls that tool once with the failure text appended as instruction.

Check idRuleSeverityRepair tool
alloc_sums_100Σ allocation_pct == 100 and every pct ≥ 0errorbuild_config
alloc_cap_45No publisher > 45% unless only one publisherwarningbuild_config
no_excluded_in_allocEvery allocation id ∈ recommendederrorbuild_config
min_publishers≥ 3 recommended (unless brief is off-category → warning with explanation)warningrank_publishers
reason_presentEvery recommended/excluded publisher has a non-empty reason ≥ 40 charserrorrank_publishers
creative_lengthsheadline ≤ 80, body 60–240, cta ≤ 24 charserrorregenerate_creative
creative_avoids_disinterestNo token from persona.disinterested_in appears in its creative (stemmed match)warningregenerate_creative
creative_uses_preferenceBrand-voice preferences respected (e.g. no "!" if preference says so)errorregenerate_creative
persona_fit_floorEvery chosen persona fit ≥ 40warningpick_personas
aov_sanityIf brief.price_tier is premium, no recommended publisher with AOV < 0.3 × implied price unless reason mentions itwarningrank_publishers
budget_sanitydaily × flight_days within ±10% of totalerrorset_budget
banned_publishersNo publisher in preferences.banned_publishers is recommendederrordrop_publisher
class ValidationResult(BaseModel):
    check: str; severity: Literal["error","warning"]; passed: bool
    message: str; target: dict      # e.g. {"publisher_id": "pub_001"} or {"persona_id": "persona_003"}
    repair_tool: str | None
Repairs are bounded (2 per interaction) and count toward the same interaction's usage — a repair never opens a new credit charge. If errors remain after repairs, the campaign is still saved with status="needs_review" and the Checks panel shows what is wrong; the user is never left with nothing.

06 · Credits

6.1 Pricing table (billing/pricing.py)

SIGNUP_GRANT = 100
TOKENS_PER_CREDIT = 4_000                     # 1 credit per 4k weighted tokens
MODEL_WEIGHT = {"gpt-4.1-mini": 1.0, "gpt-4.1": 2.0}
BASE = {"generate_campaign": 10, "regenerate_creative": 2, "chat_llm_edit": 1, "feedback_repair": 1}
def tokens_to_credits(usage: Usage) -> int:
    weighted = sum(u.total_tokens * MODEL_WEIGHT[u.model] for u in usage.calls)
    return ceil(weighted / TOKENS_PER_CREDIT)

6.2 Reserve → settle

sequenceDiagram
  autonumber
  participant O as Orchestrator
  participant C as billing/credits.py
  participant DB as Postgres
  O->>C: estimate(action) → base, est_usage
  O->>C: reserve(user, interaction, base)
  C->>DB: BEGIN; SELECT credit_balance FROM profiles WHERE id=$1 FOR UPDATE
  alt balance < base
    C-->>O: InsufficientCredits(balance, needed)
    O-->>O: abort → 402
  else
    C->>DB: INSERT credit_ledger(delta=-base, reason='reserve', interaction_id)
    C->>DB: UPDATE profiles SET credit_balance = credit_balance - base; COMMIT
  end
  O->>O: run tools (usage accumulates)
  O->>C: settle(interaction, usage)
  C->>DB: INSERT credit_ledger(delta=-tokens_to_credits(usage), reason='usage', usage jsonb)
  C->>DB: UPDATE profiles.credit_balance
  Note over O,C: on failure: release(interaction) inserts +base with reason='refund'
  • Balance is denormalised on profiles.credit_balance and guarded by FOR UPDATE; the ledger is the source of truth and a nightly job (or a test) asserts SUM(delta) == credit_balance.
  • Deterministic tools carry Cost.free() and never touch billing, so an out-of-credits user can still edit, drop, export and compare.
  • The UI's cost preview calls GET /api/credits/estimate?action=generate_campaign&brief_len=… which returns {base, est_usage_credits, balance}; estimate uses median tokens from the last 50 runs of that action (falls back to constants).

7.4 Chat — free mode

sequenceDiagram
  autonumber
  participant B as Browser (chat)
  participant API as FastAPI
  participant O as Orchestrator (free)
  participant LLM as gpt-4.1
  participant T as Tools
  participant C as Credits
  B->>API: POST /api/chat {thread_id?, campaign_id?, message}
  API->>O: run(mode=free)
  O->>LLM: messages + tool schemas + memory + campaign summary
  LLM-->>O: tool_call drop_publisher{pub_001}

  LLM-->>O: final text "Dropped Swiftcart and reallocated. Saved: never use Swiftcart."

  • Cards are typed: campaign_summary, creative, questions, validation, memory_saved, export_link. The frontend has one renderer per card type.

7.6 Memory page

  • GET /api/memory → {preferences[], facts[]} each with source (manual | chat | feedback), created_at, and origin_interaction_id.
  • Form for typed preferences (brand voice textarea, banned publishers multi-select from catalog, default budget, default bid strategy); free-text facts list.
  • DELETE /api/memory/{kind}/{id}; deletions take effect on the next interaction (memory is loaded per run).

7.7 Credits page

  • GET /api/credits → {balance, ledger[]}; ledger rows: created_at, reason, campaign_name, interaction_kind, base, usage_tokens, model_mix, delta, balance_after.
  • Sparkline of daily spend; "Get more credits" → contact toast (billing hook is POST /api/credits/grant, admin-only, unused in demo).
  • Sidebar pill subscribes to the same query; every mutating response includes credits so the pill updates without polling.

7.9 History & compare

  • GET /api/campaigns?order=-created_at lists with clarity, top_publisher, budget, status, version, errors_count.
  • GET /api/campaigns/{a}/compare/{b}?va=&vb= returns a computed diff: publisher score deltas, added/removed publishers, creative changes, config field diffs. Works across two campaigns or two versions of one.
  • Re-run = new campaign with parent_campaign_id; the compare page pre-selects parent vs child.

  • RLS on every table: user_id = auth.uid() (via join for child tables). FastAPI connects with the service role but sets request.jwt.claims per transaction so RLS still applies — a cheap second guard.
  • Interactions are the audit spine. Versions, validation results, credits, feedback and chat messages all hang off interaction_id, which is what makes the Activity timeline and the Credits ledger explainable.

Key client behaviours

  • One mutation hook (useCampaignMutation) wraps every PATCH/regenerate/feedback call: optimistic update where safe (drop, text edit), rollback on error, and writes validation + credits from the response into the caches.
  • CostPreview renders "~12 credits · 49 left" next to any paid button; disabled state with reason when balance < base.
  • ChecksPanel groups validation results by severity, links each to its target card (scrolls + highlights), and shows "Fix with AI (1 credit)" that posts feedback with the check message as the comment.
  • FeedbackButtons are on PublisherCard, CreativeCard, ConfigForm and the clarity summary; 👎 opens a 1-line comment popover; result card shows before/after with Undo (calls restore_version).
  • SSE for generation: stage list is driven by server events; a dropped connection falls back to polling GET /api/campaigns/{id} until status != generating.
